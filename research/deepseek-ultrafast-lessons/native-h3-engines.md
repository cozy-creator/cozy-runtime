# Native MiniMax H3 engines: inspected source and evidence

Research date: 2026-11-15. This is a source inspection, not a local build or GPU qualification. No model weights were downloaded and no GPU was rented. Sources below are pinned to the inspected commits; benchmark claims remain their authors' measurements.

**Yes: complete H3 inference without PyTorch already exists in public native implementations.** The strongest CUDA example here is `mmh3`; `h3-rs` is another complete Rust implementation using Candle and custom CUDA kernels; `h3-hrx` demonstrates the approach on AMD through a custom kernel DSL and runtime. They establish feasibility much more directly than extrapolating an LLM decode engine to video diffusion. They do **not** establish that a native rewrite will beat current Cozy, or that a persistent whole-model kernel is necessary.

## 1. mmh3: most directly relevant to Cozy's Rust/CUDA question

This is more than a Rust wrapper around Python. `mmh3-cuda` depends only on the local core crate; its build compiles `.cu` files with `nvcc`, links `cudart_static` and `cublasLt`, and exposes the kernels to Rust. The application calls its own text encoder and DiT in `generation::sample`, then its own video/audio decoders in `generate::run`. The production path does not require PyTorch or ComfyUI. Python remains useful for generating independent reference fixtures. This is a native model implementation, not a framework-free implementation: CUDA libraries, codecs and the operating system still participate. [CUDA manifest](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/Cargo.toml), [build and linkage](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/build.rs#L114), [conditioning and sampling](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/src/generation.rs#L574), [decoding/output](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/src/generate.rs#L19).

The useful native optimizations are concrete:

- **Persistent GEMM tiles:** one CTA per SM iterates over output tiles. Blackwell uses TMA and a two-stage shared-memory ring; Ada substitutes `cp.async`. The kernel fuses scale/bias and optional BF16 low-rank adapter contribution before rounding, with an optional SwiGLU epilogue. It requires aligned N and K shapes chosen for H3; this is not a general matrix kernel contract. Its first encounter with each shape times tile configurations and caches the winner. [Kernel implementation and constraints](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/kernels/int8_gemm.cu#L18).
- **Fused preparation and quantized attention:** DiT code combines normalization/modulation and quantization, reuses quantized inputs, and fuses QKV-related work with attention preparation. Dense BF16, INT8/FP8 attention and Sol/VSA/Veda sparse paths are separate choices. Approximation and lower precision change the computation; their gains cannot be attributed solely to replacing Python. [DiT implementation](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/src/dit.rs), [attention precision implementation](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/src/attention.rs).
- **Layer streaming:** resident layers coexist with two streaming buffers; pinned host reads/uploads overlap GPU work. Default model carriers are INT8 ConvRot DiT/text encoder, INT8 ConvRot or FP16 video VAE, and FP32 audio VAE. A 15-second 1344×768 run is explicitly described as near the 24 GB boundary on 4090, with no DiT blocks retained. This is not evidence that every full-length setting fits or runs fast. [Memory behavior](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/cuda.md#L27), [model files](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/models.md).
- **Experimental NVFP4:** DiT video rows use Blackwell cuBLASLt block-scaled FP4; text/audio rows retain INT8 because their FP4 error damages audio. Requantization keeps the INT8 weights alongside the FP4 copies, needs about 12 GB additional device memory, and is incompatible with streamed DiT blocks. The authors report visible detail loss. This is a quality/memory tradeoff, not a free speedup. [NVFP4 design and limitations](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/nvfp4.md).

**Persistent GEMM is not a persistent H3 execution engine.** The inspected CUDA sources contain no CUDA Graph capture/launch API. More decisively, `CudaDit::forward` returns host `Vec<f32>` velocities, and the ordinary generation loop updates host video/audio arrays using Rust Euler or renoise steps. It therefore still has a host-controlled denoising loop. Native code alone does not imply device-resident sampling or whole-model fusion. [Output type](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/src/dit.rs#L352), [sampling loop](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/src/generation.rs#L978).

It also has real distributed code, rather than merely an architecture proposal: Ulysses-like sequence/head exchanges, same-process GPU exchange, RDMA or socket transport, and separately assignable text/decode work. The documented two-worker 768p traffic is about 28 GB per denoising step. The relevant lesson is communication-aware decomposition; this documentation is not a matched Cozy multi-GPU benchmark. [Distributed design](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/distributed.md#L78), [CUDA shard implementation](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/src/shard.rs).

Metal is a separate implementation using Metal kernels and a Swift bridge, not a portable CUDA kernel translation. Its support matrix differs: matrix-unit paths require newer macOS; current Metal does not support NVFP4, INT8/FP8 attention or merged LoRA mode. [Metal support and limits](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/metal.md#L67).

### What its measurements establish

The authors report DGX Spark measurements at 1344×768, 124 frames, with Turbo. Dense BF16 DiT step is 38.7 s versus ComfyUI 49.7 s; Sol BF16 is 16.5 s versus 23.0 s. However, mmh3 has 37,770 tokens and ComfyUI has 38,710 from synthetic input with 1,000 text tokens. This is an explicitly unmatched comparison. The reference script uses one warmup, defaults to two timed DiT calls, and one timed VAE decode; it does not run a matched prompt-to-file comparison. [Published table](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/performance.md), [actual ComfyUI timing script](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/tools/golden/comfyui_benchmark.py).

A reported 86.29 s MP4 result includes model loading for the garden-red-panda prompt, seed 42, 75 text tokens, Turbo settings, 1344×768×124 frames. The document says the output was fully decoded for validation and explicitly labels these as individual runs. This supports reported native full-pipeline execution; it does not establish a repeatable 15-second speedup, or parity with an unmodified 30-step baseline. Other table entries omit final encoding, so they cannot all be treated as the same timing boundary. [Full-run measurements and boundaries](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/docs/performance.md#L22).

There are useful independent correctness tools and committed tiny fixtures. For example, the CUDA DiT test runs the native implementation against ComfyUI-generated fixture tensors and asserts cosine/error thresholds. That is stronger than a README assertion but smaller than a full-model, full-length audiovisual qualification. The Linux CI intentionally excludes CUDA; a green check there is not CUDA execution proof. [Actual fixture assertions](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/crates/mmh3-cuda/tests/dit_tiny.rs#L39), [CI scope](https://github.com/mmh3-org/mmh3/blob/9c0652f4c39fd67ed2330aeafd61e95a1fe7e375/.github/workflows/commit-check.yml#L49).

## 2. h3-rs: native Rust with a tensor library and custom fused CUDA

The current tree differs materially from [the originally supplied 0.3.0 documentation](https://docs.rs/crate/h3-rs/0.3.0). Its 0.5.3 manifest supports both CUDA and Apple Silicon MLX. CUDA uses Candle tensor operations plus NVRTC-compiled kernels; it does not depend on libtorch. The `Engine` source performs conditioning, sampling and both decodes, rather than stopping at an attention or DiT operator. [Current manifest](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/Cargo.toml), [Engine orchestration](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/src/pipeline.rs#L467), [backend selection](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/src/backend.rs).

The custom kernel source contains INT8 QK with FP16 PV attention, explicit `mma.sync`, asynchronous copies, and a 128×128 INT8 GEMM with a three-stage copy pipeline. SwiGLU can be an epilogue. These are regular CUDA kernels compiled from embedded source strings, not a new whole-model DSL or a persistent distributed task scheduler. No CUDA Graph capture/launch implementation was found in its own inspected source. [Actual kernel source and NVRTC compilation](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/src/attn8.rs#L249).

Supported carriers include INT8 ConvRot FL2VA/Ref2VA, an NVFP4+AWQ text encoder decoded by layer, FP16 video VAE and FP32 audio VAE. Its shape contract rounds dimensions to multiples of 32 and frames to `17k+5` at 24 fps. CUDA installation targets Ampere or later; streaming presets trade GPU residency against RAM/mapped-file reads. The Apple path packs INT8 weights into MLX format, while Candle/MLX activation boundaries currently materialize buffers. Thus the Apple path's existence does not prove zero-copy integration or CUDA-equivalent performance. [Carriers and shape/memory limits](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/README.md), [frame alignment code](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/src/pipeline.rs#L295).

Its 4090 table reports **13.0 s versus 15.6 s** for one 1344×768×124-frame DiT step, and **0.52 s versus 0.47 s** for 640×352×56 frames. Native is slower in the small case. The checked-in ComfyUI script makes synthetic 30-token context, times three forwards, and prints all three; the README does not supply a paired full-pipeline campaign, variance, exact reference commit, or complete per-side provenance. Do not turn this into a general 1.2× engine claim. [Timing table](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/README.md#L183), [reference benchmark source](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/tools/bench_comfy.py).

The parity tool computes and prints maximum/mean error and cosine similarity against ComfyUI dumps, but its `report` function does not fail on an error threshold. It is a useful diagnostic, not by itself an automated acceptance gate. Likewise, CUDA release packaging checks linkage on a runner without a GPU; it does not execute the generated video pipeline. [Parity report implementation](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/src/bin/parity.rs#L12), [release validation scope](https://github.com/apiplant/h3-rs/blob/7c9f3d78e2c5cefd6f5ab6d6b84bb1d82f65e9e6/.github/workflows/release.yml#L118).

## 3. h3-hrx: strongest separate example of a custom native execution stack

This is a full H3 port for AMD Strix Halo, not CUDA. The dependency boundary is Rust model code → Loom kernel artifacts → HRX buffers, transfers, queues and graphs. `Session` exposes text/vision conditioning, denoising and video/audio encode/decode. Source includes custom attention, GEMM, normalization, convolution and sampler kernels. No ROCm headers or `hipcc` are required by the documented application build; it provisions an HRX native bundle and Loom compiler instead. [Responsibilities and dispatch](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/shared-hrx.md#L1), [Session implementation](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/src/session.rs), [setup requirements](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/setup.md#L1).

Euler/ResMultistep maintain evolving latents on the device, including multistep history; CPU schedule coefficients remain outside. Optional `H3_GRAPH=1` records one replay per transformer block, with explicit graph lifetimes and invalidation when storage changes. The source constructs a separate graph for each block. Cooperative scheduling fences at block boundaries to admit other work; it does not preempt kernels. This is useful material for studying graph ownership and scheduling granularity, not proof of a single persistent H3 mega-kernel. [Resident sampler and graph design](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/shared-hrx.md#L76), [actual graph construction](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/src/stack.rs#L1129).

Default model carriers use INT8 ConvRot DiT/text encoder, FP16 video VAE and FP32 audio VAE. Mixed BF16/INT8 transformer blocks have explicit layout requirements. Default attention is INT8; FP16 and experimental INT4 paths exist, with optional VSA sparsity separate from precision. Other GPUs are explicitly unvalidated. [Model and layout contracts](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/setup.md#L54), [attention and benchmark controls](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/performance.md#L138).

Its strongest public execution evidence is concrete media plus disclosed end-to-end settings: two 1344×768, 124-frame, 24 fps clips with audio, 20 ResMultistep evaluations, seed 0, full attention and no step caching. On 128 GB Strix Halo at historical commit `a526090`, reported durations are **31m57.36s** and **31m48.84s**, including local weight loading, conditioning, sampling, decoding and encoding, excluding downloads and later trimming. `--steps 21` means 21 sigma points and 20 evaluations here. These two examples prove neither NVIDIA performance nor a matched comparison against PyTorch. [Prompts, settings, timings and video links](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/showcase.md#L1).

Its benchmark methodology is worth borrowing: distinguish cold process from cold disk; disable profiling during latency measurements; compare kernel, block, model and complete render; preserve exact arithmetic/output evidence; retain the source checkout because benchmarks read kernel sources. The repository includes Criterion benchmark code and independent Torch/ComfyUI parity tools, while explicitly admitting incomplete numerical coverage. A replay digest proves repeatability, not perceptual quality. [Measurement protocol](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/performance.md), [independent references and coverage gaps](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/testing.md#L58).

**Current maintenance caveat:** Cargo specifies HRX 0.12.0 but also says this HEAD requires an unreleased `NativeSession::run_cooperative` API and a local development override. The pinned HEAD's [CI run](https://github.com/zacharydenton/h3-hrx/actions/runs/41309752597) failed in “Formatting, lint, and CPU tests”; later package verification was skipped. The job summary does not establish the failure's root cause, and this inspection did not build it. Treat the current tree as a study source, not a verified drop-in dependency. [Explicit development dependency](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/Cargo.toml#L84), [required override](https://github.com/zacharydenton/h3-hrx/blob/796c521d0748ff262a3ca96218b1f32a3eefea1d/docs/shared-hrx.md#L14), [failed job](https://github.com/zacharydenton/h3-hrx/actions/runs/41309752597/job/124857449166).

## Recommendation for Cozy

1. **Use mmh3 as the first CUDA implementation to study and selectively reuse.** Its model-shaped INT8 preparation/GEMM/epilogues, quantized attention, VAE kernels and reference fixtures are concrete candidates. Qualify each against Cozy's tensor/layout/lifetime contracts and target GPU; do not import its controller, worker protocol or memory policy merely because they accompany the kernels.
2. **Use h3-rs as an independent model/format reference and a second fused-kernel candidate.** It is particularly useful for ComfyUI carrier handling, ConvRot/AWQ/LoRA semantics, and studying how much can remain ordinary native tensor operations. Adopting Candle is a separate design choice, not a requirement for borrowing the kernel ideas.
3. **Study h3-hrx for device-resident sampling, explicit graph lifetimes and block scheduling.** Its Loom/AMD kernels are not directly reusable CUDA. Replacing Cozy's native runtime with HRX would be a separate platform project and is not justified by these measurements.
4. **Build the intended native H3 path, then compare unchanged workloads before adding approximation.** For new Cozy performance/quality evidence, retain the full-length target of 15 seconds, 362 frames, 1344×768, 30 steps and audio. Freeze model/adapter hashes, context/noise, sampler, precision, attention and hardware; separate loading, conditioning, denoising, VAEs and media encoding; report cold/warm cache state and repeated samples. Then evaluate sparsity, fewer-step adapters or FP4 as separate changes with audiovisual quality checks.
5. **Do not promise a speedup from the language switch.** The public evidence shows full native inference is feasible and targeted fusion can help. It also shows small native workloads can lose, memory transport remains significant, and a native engine may still use host sampling. The next defensible performance claim requires a matched Cozy baseline, not ratios assembled from these unrelated tables.
