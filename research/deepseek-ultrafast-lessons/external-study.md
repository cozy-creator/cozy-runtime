# DeepSeek Ultrafast: what the implementation actually specializes

Inspected on 2026-11-15 at upstream `main` commit [`76766a97308bfd1658fb055e835d0f92de737dc3`](https://github.com/basetenlabs/deepseek-ultrafast/tree/76766a97308bfd1658fb055e835d0f92de737dc3), confirmed with `git ls-remote`. This is source inspection and review of first-party documentation; no builds, GPU runs, or independent performance measurements were performed.

The transferable idea is to specialize **the execution plan, data representation, kernel boundaries, and communication for an important workload and hardware class**. This repository implements a graph of specialized CUDA kernels. It does not demonstrate that a whole-model megakernel, an exact GPU SKU, or CUDA C++ instead of a GPU DSL is the essential cause of its reported speed.

## Kernels, fusion, persistence, and graphs are separate mechanisms

## Specialization is more precise than “one model, one GPU”

The declared target is DeepSeek-V4.1-Flash on `sm_100a` and `sm_103a`. Supported configurations include B200, B300, and GB300 with four or eight GPUs; the README does not claim arbitrary GPU support. [Requirements](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/README.md#L26-L43).

Dispatch combines several dimensions:

- **Architecture and tensor parallel degree:** profiles select `(10,3) × TP4`, `(10,3) × TP8`, or a base path, and choose different draft-block/confidence settings. [Profile definitions](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/cuda/src/profile.rs#L4-L64).
- **Exact model shapes:** SGL requires hidden width 5120, local expert widths 576 for TP4 or 288 for TP8, and specific expert/top-k counts. These are implementation eligibility conditions, not general transformer properties. [Weight dispatch](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/weights.rs#L421-L440).
- **Small decode row count:** the optimized speculative path is limited to eight verification rows; the source explicitly rejects a switch to a differently rounded GEMV path. [Numerical constraint](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/model.rs#L2449-L2462).
- **Resources:** SM count is queried, while SM100/103 shared-memory budgets are explicitly selected; some launch choices query active cluster capacity. This is architecture/resource tuning rather than a lookup of the GPU product name. [Hardware configuration](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/ops.rs#L195-L232), [occupancy-based choice](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/ops.rs#L1453-L1471).

The hardware dependence is substantive: [inline PTX allocates TMEM and issues `tcgen05` block-scaled MMA](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/tc.cuh#L43-L61), and [SGL issues TMA transfers with cache hints](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/variant_zzzzzzzzzzsgl.cu#L29-L45). RTX 5090 and RTX PRO 6000 Blackwell are CC12.0, whereas B200 is CC10.0 and B300/GB300 are CC10.3. [NVIDIA GPU table](https://developer.nvidia.com/cuda/gpus). NVIDIA's math-library documentation explicitly distinguishes the SM100/103 `tcgen05` path from SM120. [Architecture distinction](https://docs.nvidia.com/cuda/cublasdx/performance_guide_api_blackwell.html). Reusing the plan on H100, Ada, or RTX Blackwell therefore requires different kernel implementations/resource choices; a build-flag rename is not a port.

## Quantization is a representation contract

- **Dense FP8:** the loader checks `F8_E4M3`, reads a separate scale tensor, and interprets E8M0 scales per 32×32 weight block. [Loader and decoding](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/weights.rs#L254-L274).
- **Routed expert FP4:** packed E2M1 weights have one E8M0 scale per 32 values. [Packed shape checks](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/model/src/packing.rs#L3-L16), [actual E2M1/E8M0 decode](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/gemv.cu#L370-L394). The SGL tensor-core path combines E2M1/E4M3 operands and quantizes intermediate activations to E4M3 with exponent scales. [MMA selection](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/variant_zzzzzzzzzzsgl.cu#L296-L310), [activation packing](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/variant_zzzzzzzzzzsgl.cu#L407-L425).
- **Cache FP4 is distinct:** the offload code supports group-16 E4M3 scales and group-32 power-of-two scales. Calling everything “FP4” would lose meaningful semantics. [Pack/unpack implementations](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/kv_fp4.cu#L3-L71).
- **Execution layouts:** weights are repacked into tiled and row-major/scale-block forms consumed by particular kernels. Preserving the quantization encoding is separate from selecting this execution layout. [Packing implementations](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/model/src/formats.rs#L145-L179), [row-major/scale layout](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/model/src/formats.rs#L208-L235).

## Communication is part of the optimized computation

The examined TP communication kernel directly stores contributions into peer receive buffers, polls arrivals, reduces them, and calls a fused output epilogue. These are custom device protocols, not merely a Rust wrapper around an all-reduce call. [Peer writes, polling, reduction](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/comm.cu#L620-L707), [hyperconnection/output epilogue](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/comm.cu#L105-L130). The specialized FFN communication path can consume completed rows while other producer work remains outstanding. [Lamport-style polling path](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/cu/variant_zzzzzzzzzlp.cu#L255-L295).

Inference for Cozy: communication/computation overlap and epilogue fusion are worth investigating if the target trace shows exposed collective time. Their benefit cannot be assumed across interconnects, parallelism strategies, or payload sizes from this source alone. Names such as `nvls` are also insufficient evidence of a particular hardware collective mechanism; inspect the actual instructions above.

## CUDA versus DSL is the wrong binary choice

| Authoring route | What first-party documentation actually permits |
|---|---|
| CUDA C++ plus inline PTX | This repository directly expresses architecture instructions, barriers, cache hints, producer/consumer roles, and custom peer communication. That control is visible in the source cited above. It does not establish a measured advantage over an equivalent DSL implementation. |
| Triton | The official tutorial implements persistent matmul, TMA, warp specialization, and Blackwell two-CTA variants. The API also permits inline assembly; that API has its own operand/packing restrictions. [Persistent matmul](https://triton-lang.org/main/getting-started/tutorials/09-persistent-matmul.html), [inline assembly](https://triton-lang.org/main/python-api/generated/triton.language.inline_asm_elementwise.html). |
| CuTe DSL | Explicit layouts, memory/thread hierarchy, copy/MMA atoms, and asynchronous pipeline coordination are part of the programming model. NVIDIA says generated kernels aim to match C++ CUTLASS, while acknowledging possible gaps from missing optimizations. [Overview](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/overview.html). |
| TileLang | Its documented instructions expose shared memory, TMA, barriers, warp-group operations, and register-allocation controls; higher-level copies can also be lowered by the compiler. [Instruction documentation](https://tilelang.com/programming_guides/instructions.html). |

Inference: choose the lowest level needed to express and tune the actual bottleneck. A DSL kernel can still be model-specific, shape-specific, persistent, fused, and architecture-specific. Conversely, handwritten CUDA can leave expensive intermediate traffic or poor scheduling intact. Establish a language limitation with the same algorithm/layout/schedule and generated-code evidence, rather than comparing an aggressively specialized CUDA implementation against a generic DSL baseline.

## Compile before deployment is independently transferable

The Rust build invokes `nvcc -cubin`, embeds the resulting bytes, and compiles `variant_` files only for `sm_103a`. Runtime loads those embedded modules; the container copies the built executables into a CUDA runtime image. [Build](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/build.rs#L8-L56), [module loading](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/kernels/src/lib.rs#L5-L44), [container](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/deploy/Dockerfile#L13-L28).

This does not require abandoning DSLs: CuTe documents exporting precompiled C headers and object files, including kernels, for C/C++ integration without production JIT compilation. Its C++ integration also lists required runtime libraries. [CuTe AOT guide](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/guides/ahead_of_time_compilation.html). Architecture-specific `a` targets have restricted compatibility; ship appropriate compiled artifacts rather than assuming an SM100/103 cubin covers other Blackwell classes. [NVIDIA compatibility guide](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/index.html).

## What the performance evidence does and does not establish

Baseten reports 1,740 coding tokens/s on four GB300s and 2,060 on eight B300s, with step times 3.30 ms and 2.71 ms. These are speculative decode numbers: the README reports an average 5.6 emitted tokens per step, names the Tetris prompt, and provides reproduction instructions and 30-run ranges. It separately reports million-token prefill. [Reported results and conditions](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/README.md#L5-L14), [timing script and ranges](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/README.md#L89-L124).

Those results do not isolate the contributions of quantization, speculation, CUDA Graphs, PDL, fusion, communication, or language choice. No such ablation appears in the cited performance report. The included block-verification harness checks sampling against a reference and TP agreement; that is a narrower scope than model-wide quality validation. [Verification assertions](https://github.com/basetenlabs/deepseek-ultrafast/blob/76766a97308bfd1658fb055e835d0f92de737dc3/crates/engine/src/bin/test_block_verify.rs#L251-L286).

## Transfer to H3 and broader Creator work

These are proposed investigation directions, not demonstrated H3 improvements:

1. **Specialize repeated regions using measured workloads.** Consider model family, shape bucket, dtype/layout, architecture, and parallel degree together. The evidence for this approach is the multidimensional dispatch above; it does not require one permanent fork per GPU product.
2. **Measure kernel boundaries before increasing fusion.** Start with expensive normalization/modulation, quantization/dequantization, layout conversion, residual/activation epilogues, and redundant materialization where the local trace proves their cost. Compare selective fusion against graph replay and against a pipelined multi-kernel alternative, reflecting the actual SGL design.
3. **Prepare layouts and execution state outside repeated work.** Treat the packed representation and launch plan as reusable implementation details. Preserve the logical tensor encoding and numerical behavior while changing the execution representation.
4. **Use architecture-specific kernel implementations behind stable operator contracts.** Preserve useful CUDA, Triton, CuTe, or TileLang implementations according to measured end-to-end results. Reuse AOT packaging where it fits existing builds.
5. **Adapt communication only when the target parallel plan justifies it.** DeepSeek's TP all-reduce fusion is an idea to evaluate, not a replacement algorithm for a different model's sequence-parallel attention.
6. **Separate algorithm changes from implementation changes.** Speculative token decoding, DeepSeek-specific expert routing, compressed autoregressive caches, and the eight-row regime do not supply a drop-in diffusion speedup. Any proposed timestep reduction, reuse, approximation, or new quantization needs its own quality comparison. For implementation claims, hold model/settings/output criteria fixed and report both operator and end-to-end timing boundaries.
