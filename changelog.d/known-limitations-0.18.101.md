Known limitations in 0.18.101.
- With about 3 GiB of device memory free and a second model resident on the GPU, a warm run can end `device_shortfall` at its VAE decode, after its denoise has completed, instead of making room and finishing (run 3143: needs 438 MB, 107 MB available). The fix follows in 0.18.102.
- A multi-GPU group that cannot form stalls instead of failing fast. The one cause seen, NCCL peer memory over PCI on 2× A40 pods, is fixed in this release (a group's GPUs use peer memory only over NVLink). For any other cause the executors still wait in the group's first barrier, no weights load, and after about 11 minutes the run ends REFUSED with "Retained preparation is unavailable" rather than FAILED with the cause; 0.18.99 behaves the same. A bounded formation that fails with its reason follows in the next patch.
- An executor's first run is slower than its later ones: on an L4, SDXL's first run after a Runtime update took 11.2 s and its second 8.5 s, against 7.9 s in steady state (0.18.99: 7.8 s). No kernel compile was running; the first calls pay their own first launches now that the warm render is gone.
- TensorFS 0.3.92's device copies from page-cache mappings are being removed in TensorFS 0.3.93; they are neutral on pods running at full CPU.
